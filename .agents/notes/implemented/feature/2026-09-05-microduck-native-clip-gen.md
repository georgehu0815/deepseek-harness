# Agent Note: Native MicroDuck Clip Gen and authored-pose workspace

Status: implemented

English | [中文](2026-09-05-microduck-native-clip-gen.zh.md)

## Problem

An authored robot reference needs a usable path from an activity request to joint targets, visual review and a portable recording. A video of posed geometry cannot demonstrate learned control, balance or hardware safety. A separate application or independent editor store would also detach the reference under review from the session and the exported video. Raw servo names and unlabeled scalar values make it difficult to identify the body part a control affects; an anatomical illustration that does not match the installed robot can mislead the same review.

## Decision

[Clip Gen](../../../../packages/client/ui-robot-lab/README.md#clip-gen) contributes a native central authoring tab and a right-hand Simulation workspace. Both bind one declared session-scoped interaction store, distinct from server records and the policy playback owner. The existing Micro Duck Train/Evaluate controls and Robot Studio retain their separate responsibilities.

The planner expands supported English or Chinese action clauses and dance/greeting requests into ordered recipes; it does not invoke a language model. Compilation uses the installed model's fourteen ordered servo targets and limits. Linear keyframes, separate free-root pitch and coupled rig projections support editing without claiming dynamic feasibility. Imported JSON is checked for version, complete key/duration limits, ordering and servo bounds before replacement.

The Animate dance picker bundles six original model-bound sequences and six larger v2 revisions rather than reading a developer's filesystem or rerunning a recipe. The v2 revision label is distinct from its schema-3 format: solved root motion and support intervals preserve sampled foot geometry, with the existing pose-edit and training locks. Selection validates the installed fingerprint, joint order, motion limits and export byte budget before copying targets, BPM and the original timed guide into the shared draft. The action picker resets after selection so reloading the same original is explicit. Editing never mutates bundled assets; replacing a timeline stops playback and invalidates review. The picker does not populate the browser's saved-guide library. Keeping authored assets in the client bundle makes them available on every browser without adding a server operation or implying numerical retargeting from G1 anatomy.

Each dance selection also binds an explicit soundtrack id in the session draft; editable names never select audio. Twelve embedded original genre recordings avoid external music requests or commercial samples. Simulation owns one media element, whose time drives the shared motion playhead; retiming scales the audio clock and playback rate. Pause, seek, loop, speed, mute and volume stay in that owner. Replacement, hidden tabs, unmount and capture silence it; cleanup revokes late play failures. Media errors stop motion visibly rather than falling back to silent playback. Unrelated timeline imports clear the id, while pose/name edits retain it. Audio is excluded from exported JSON and saved sequences; the existing Studio music transport remains separate. The [selectable-music decision](2026-09-07-clip-gen-selectable-music.md) adds credited alternatives and a shared preview/export timing plan while retaining this original-rhythm path.

Whole-body heading belongs to a browser-only version-2 clip, not the version-1 training reference. Every preview key carries a finite `rootYaw` bounded to ±2π radians. Unwrapped linear angles preserve a complete left/right turn; forward kinematics applies world-Z heading before local-Y pitch. Editing heading promotes all legacy keys explicitly, and keying, playback and matching video JSON retain the heading. Training controls, custom clip parsing and backend version/key validation reject preview motion instead of dropping heading. The forty-beat turning example coordinates leg gestures with root animation; it does not solve planted-foot contact or qualify physical turning. Version-1 SequenceByAI and saved guide sequences remain training-reference-only.

Walking turns use a separate version-3 preview with model-bound, baked leg targets, root translation/roll and explicit rigid stance-foot intervals. The compiler solves two ankle-body poses with ten leg servos, root XYZ and roll, while prescribing yaw and zero pitch. A small damped numerical solve remains private to this task; failure cannot authorize a root-spin substitute. Preserving each supporting foot's position and orientation prevents geometric sliding without claiming contact forces, center-of-mass support or dynamic balance. Playback uses the same native FK and a fixed standing-floor offset. Import checks sampled interpolation drift as well as keys; nonoverlapping per-foot intervals bound the work even for hostile files. Exact neutral endpoints retain loop continuity. Pose/key mutations are blocked at store actions and controls, while retiming scales contacts alongside keys. Training admission rejects the version, and legacy parsers reject smuggled root coordinates. The version-3 file remains an authored kinematic reference, not a learned walking skill; [the package README](../../../../packages/client/ui-robot-lab/README.md#clip-gen) owns the format and user controls.

Activity plan's Dance guide library keeps reusable content separate from the live session draft. Its root-scoped `conversation.clip-gen.guides` child slot owns an independently declared protected store. Text-only selection fills the current session's prompt; a guide with an exact sequence loads its validated timeline without starting playback, training or export. Three built-in guides are reconstructed from the active locale rather than persisted. Their prose remains example input, not a promise of exact repetition counts from the deterministic planner. The [SequenceByAI decision](2026-09-05-microduck-session-sequence-ai.md) owns current-agent generation, correlated result import and saved exact timelines.

Custom guides preserve descriptions verbatim and trim only outer whitespace from names; neither field is translated. Add guide opens a name/description editor prefilled with the current activity prompt; saving requires a nonblank trimmed name of at most 80 characters and a nonblank description of at most 2,000 characters, with duplicate custom names rejected case-insensitively. Users can add many cases within the storage limit; custom editing and deletion are not provided. Only `guides` and `nextId` persist, including a guide's optional exact model-bound sequence, not unsaved editor inputs, subsequent animation edits, media or evidence. This browser-local library is shared across sessions and reloads on the same origin, browser and profile, not synchronized through a server or account.

Protected storage uses the existing `draftMaxBytes` configuration as `maxFileBytes` for the complete library envelope. Saved, pending and blocked status distinguish durable browser writes from in-memory additions. Invalid saved bytes, quota failures and conflicts preserve existing storage without silent replacement; a blocked in-memory guide remains usable but has no durability guarantee. The [protected recovery owner](../../../../packages/client/store/README.md#browser-recovery) defines locking and revision checks.

The preview uses actual backend meshes and optional `RobotScene.kinematics` rest transforms, hinge anchors and reference positions. Browser forward kinematics renders the authored pose without stepping physics. Missing metadata makes live posing and video generation unavailable; it does not authorize a guessed skeleton. The [Robot reference](../../../../docs/subsystems/robot.md) owns the scene fields.

Companion ducks are controlled poses in that same canvas, not separate physics simulations or editor timelines. A default follower derives Duck 1's current pose, so later motion replacement and unkeyed inspection do not leave stale copies. Independent choices retain validated preset bytes and model identity, sampled at the primary beat position; looping selections repeat and non-looping selections clamp at their end. The existing `maxGroupMembers` configuration bounds the displayed group. One shared clock and soundtrack avoid independent starts or competing music, and the primary duration gives both MP4 entry points one unambiguous end.

The scene owns shared body geometry; actors own their transforms and materials, so removing a companion does not dispose meshes still borrowed by others. Formation spacing and camera bounds derive from standing model dimensions and group size, not every moving pose. Duck 1 alone remains a gesture target. Localized sprite labels live inside the canvas, so they identify the same ducks in preview and MP4 rather than disappearing as HTML overlays. Group changes invalidate review and lock during capture. A completed video's frozen duck count describes that capture even after the displayed group changes.

The accompanying JSON remains the exact primary clip rather than inventing a multi-robot training format. Multi-duck output explicitly labels it as Duck 1 only; companion choices and presentation offsets remain transient session state. Keeping this distinction prevents a rendered group from being mistaken for a reproducible multi-agent physics experiment or a training reference for several controllers.

Authoring control icons reuse one memoized set of [SVG artwork](../../../../packages/client/ui-robot-lab/src/client/clip-part-artwork.ts) for the loaded scene and profile. The artwork projects the installed mesh vertices at the neutral STAND pose and highlights parts assigned to the relevant joints within a muted whole-duck context. It uses current geometry and joint ownership, not copied part coordinates or test-fixture silhouettes. Missing kinematics or incompatible joint order produces a generic mechanical fallback, not a claim about unavailable anatomy. These static locator icons neither replace the live pose preview nor create per-control WebGL renderers.

Localized joint labels retain raw model names for exact identification. Joint and root values display radians and degrees; control help distinguishes installed limits/defaults from measured behavior, the robot's own left/right sides from screen directions, and model-local angle signs from intuitive movement names. Rig help describes coupled movement, names the joints limiting its range and identifies its scalar as an adjustment rather than a physical joint angle. Rounded display values do not replace the actual limits or defaults. Each control card explicitly labels its slider, so clicking decorative artwork cannot activate a nested reset button. These presentation additions use the existing actions and keying rules; they add no model context, tool call, training, physics or export behavior.

The right workspace exposes the shared pose controls rather than owning a second robot draft. Exact numeric angles and rig amounts use the same installed limits and mutations as sliders. Environment and camera settings occupy session-local view state: floor materials, grid, axes, lighting, background and wireframe affect drawing, not physics or clip JSON. Orbit and Pan disable pose picking; Pose permits existing hinge gestures. View changes and preview speed do not invalidate motion review or conflict with pending AI imports, while capture locks them to prevent mid-recording scene changes. Preview speed scales only the interactive clock; recording retains authored timing. This keeps visual inspection independent of training admission and avoids controls that imply unsupported gravity, friction or motor simulation.

Manual verification records review of one authoring revision, not a measured assessment. Edits invalidate verification; unkeyed pose edits block playback, saving and generation until explicitly keyed. Generation captures the reviewed reference and starts one sequence at zero. Preview looping does not extend a recording. The renderer owns visibility and playback; each recorder owns its canvas stream, cloned audio tracks, timers and event listeners. Cancellation and unmount cannot publish an obsolete result, and recorder settlement releases owned capture resources.

The default-on **With audio** preference selects both the automatic download and the completed-file links. A soundtrack-bearing capture prepares two native recordings over the same canvas: silent video and video plus a private Web Audio destination. Both recorders become ready before the soundtrack and shared motion clock start. Resampling fits the authored duration, including pitch; preview volume, mute and speed do not alter the exported track. No microphone or speaker stream is recorded. Encoder failure, interruption or cancellation stops the peer before the graph closes; decoding and resume waits have bounded deadlines. No soundtrack creates only a video recording.

Retaining both variants costs two encoders and two blobs when music exists, but lets the saved-file checkbox change actual bytes immediately without recapturing or mixing a completed video with a later draft's soundtrack. Plugin disposal, replacement and late publication revoke both URLs. The rendered viewport stays size-locked during capture; startup waits for stable layout and framebuffer dimensions, and a subsequent framebuffer resize rejects the recording rather than publishing mismatched H.264 parameters.

MP4 export negotiates supported `MediaRecorder` MP4 codecs, preserves the actual MP4 MIME and checks container identity, the presence of a movie metadata box and a nonempty media payload. Soundtrack variants also require an audio-track handler in the MP4 metadata. It rejects unsupported browsers, encoder errors, empty or malformed output and bounded startup/finalization failures. It neither renames WebM nor calls a transcoding service. Matching JSON preserves the reference recorded in each completed video independently of later edits; browser downloads are user-managed files, not server artifacts or training admission.

## Alternatives considered

**Embed the standalone editor or reuse its global stores.** That retains another application's transport and mutable ownership. Native slots and a shared session store keep the central editor and right preview on the same reference without another server.

**Render a decorative robot without installed kinematics.** Such a preview cannot establish how the actual model's servo order, rest transforms and hinge axes produce the target. Missing metadata is an explicit unavailable state instead.

**Give every control a live 3D canvas or a hand-drawn anatomical thumbnail.** Many renderers would duplicate scene work for static part identification, while copied geometry would drift from the installed model. Shared model-derived SVG artwork keeps the locator consistent without extra WebGL contexts; its honest fallback leaves the text usable when that mapping is unavailable.

**Add heading as an optional training-reference field.** A consumer that copies only servo angles and pitch can silently discard the requested turn. A distinct browser clip version makes unsupported training fail, including when every heading is zero. Quaternion shortest-path interpolation is also unsuitable for authored full turns because equivalent endpoint orientations can erase their winding.

**Give each duck its own canvas or playback transport.** Separate renderers duplicate model resources and require another compositor to include the group in an MP4. Independent clocks can drift or start late. Shared drawing and sampling make the recorded canvas the one under review without claiming multi-robot dynamics.

**Export WebM with an MP4 filename.** A renamed container does not satisfy MP4 playback or export requirements. Native MP4 support is mandatory; a failed encoder produces no completed video.

**Add a WebCodecs encoder and MP4 muxer immediately.** No maintained MP4 muxer is an existing dependency in this checkout. Native `MediaRecorder` avoids a new encoding implementation and dependency while making unsupported-browser behavior explicit; it does not promise offline, frame-exact or universal-browser export.

## Consequences

Users can inspect and export model-derived references without a model key, training run or hardware command. The cost is real-time recording with the browser tab and Simulation workspace visible; offline rendering, dynamic feasibility and learned performance are outside this operation. Native startup, stop scheduling and rendered-frame cadence can make encoded duration differ from authored duration; capture is not frame-exact. Container checks are not a decoder-level guarantee of scene content.

Clip Gen drafts and media remain transient browser state. Users retain both the MP4 and its matching keyframe JSON before refresh. Later custom training consumes version-1 JSON through the existing training workflow, never preview-only versions 2/3 or the MP4. Manual review and successful export do not qualify a policy or override hardware blockers.

The executed [motion tests](../../../../packages/client/ui-robot-lab/tests/clip-motion.client.spec.ts), [store tests](../../../../packages/client/ui-robot-lab/tests/clip-gen-store.client.spec.ts) and [recorder tests](../../../../packages/client/ui-robot-lab/tests/clip-video.client.spec.ts) cover recipe recognition, bounded fourteen-joint targets, interpolation, rig limits, imported JSON, revision and unkeyed guards, key editing, MP4 negotiation, rejected output and cancellation races. These source checks do not establish built-browser rendering or actual codec availability; the assembled browser workflow and real MP4 playback require separate evidence.

The [assembled walking preview](../../../../apps/web/tests/clip-walking-preview.e2e.ts) snapshots the built plugin's complete left/right headings, guide, key count and disabled training path. These checks concern kinematic references and UI composition, not rendered pixels, contact forces or physical balance.

The [companion tests](../../../../packages/client/ui-robot-lab/tests/clip-ducks.client.spec.ts), [selection tests](../../../../packages/client/ui-robot-lab/tests/clip-duck-controls.client.spec.tsx) and [two-entry capture tests](../../../../packages/client/ui-robot-lab/tests/clip-duck-capture.client.spec.tsx) pin follow/independent timing, bounded rosters, capture locks and the frozen count/primary-JSON distinction. Those checks do not assert physical interaction or decoder-level MP4 pixels.
